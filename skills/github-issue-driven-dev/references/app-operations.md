# 30アプリ継続運用の標準

この文書は、複数アプリを長期間運用するときの標準的な目標構成を定義する。外部サービス側の設定状況とは分けて扱い、未設定の機能を「導入済み」と記録しない。

## 基本方針

- 日常開発はCodexを中心にする。Devinは隔離VM、長時間テスト、並列作業、独立検証など、Codex単体では扱いにくい作業に限定する。
- アプリごとに監視、デプロイ、秘密情報管理をばらばらに作らず、共通基盤を1つ整備する。
- 自律実行の範囲を広げても、リリース、セキュリティ、費用、権限、廃止の最終責任は人間が持つ。
- A段階（本番）だけにOncallを適用する。B段階（β）とC段階（実験）は、低コストな監視と定期確認に留める。
- 監査と修正を分離する。Security ScanとOncallの結果確認は読み取り専用とし、修正は別Issue・別セッションでDraft PRまでにする。
- 自動マージ、本番デプロイ、権限変更、データ削除、課金追加を自律実行の対象にしない。

## iOS・デスクトップアプリの実行環境

コード編集、静的解析、ログ確認など画面を占有しない作業はCodexのローカル実行でよい。一方、iOSアプリとデスクトップアプリで、Simulator、実機、ブラウザ、GUI操作を伴う開発・検証は、DevinのクラウドVMまたはOS対応の専用リモート環境を既定にする。

これは、ローカルのComputer Useがユーザーのブラウザやデスクトップを占有し、プロンプト入力中や別作業中に割り込むことを避けるためである。バックグラウンド実行や定期実行のエージェントは、明示承認なしにユーザーのローカル画面を操作しない。

| 対象 | 既定の実行環境 | 補足 |
| --- | --- | --- |
| iOS / iPadOS | Simulator・実機へ接続できるリモートMac | Linux VMだけでXCUITestや署名を代替したと扱わない |
| macOSデスクトップ | リモートMac | ローカル画面を占有する操作は事前承認を必要とする |
| Windowsデスクトップ | WindowsクラウドVM | 対象OSでビルド・操作・証跡取得を行う |
| Web UI | ヘッドレスブラウザまたはリモートブラウザ | ローカルで可視ブラウザを勝手に起動しない |
| コード編集・静的解析 | Codexのローカル実行 | ネットワーク制限と秘密情報の取扱いを守る |

リモート環境がない、またはOS固有の検証を実行できない場合は、対象ケースを「未検証」として理由と代替手段をIssueへ記録する。ローカルComputer Useへ切り替える場合は、必要性、操作対象、ユーザーへの影響、所要時間を提示し、事前承認を得る。

リモート環境でも、認証情報、個人情報、トークン、Cookieを依頼文や証跡へ含めない。テスト用アカウントは既存のシークレット機構から渡し、画面・動画・ログは秘密情報を除去してIssueまたはPRから参照できる場所へ保存する。

## 共通基盤

30アプリへ展開する前に、次の共通装備を一度だけ用意する。

1. **サービス台帳**: リポジトリ、公開URL、所有者、段階、データ分類、監視、バックアップ、費用上限、廃止予定を記録する。
2. **リポジトリ標準**: Issue / PRテンプレート、AGENTS.md、CI、依存更新、Secret検出、ライセンス確認を共通化する。
3. **デプロイとロールバック**: 再現可能なデプロイ、直前バージョンへの復旧、リリース判定基準、承認者を定義する。
4. **監視**: Sentryなどのエラートラッキングと、外部URLの外形監視を用意する。
5. **バックアップ**: 対象データ、頻度、保持期間、暗号化、復元手順を決め、実際に復元試験を行う。
6. **Secret・権限管理**: 長期トークンをリポジトリへ置かず、最小権限、所有者、ローテーション、失効手順を定める。
7. **費用上限**: 各クラウド、監視、AI、通知サービスの予算アラートと停止条件を決める。
8. **通知基盤**: 障害とセキュリティをSlackへ集約し、重大度に応じたLINE中継を用意する。
9. **廃止ルール**: 利用者への告知、データのエクスポート、Secret失効、DNS・ドメイン・外部連携の解除、台帳更新を定義する。

## 監視の3段階

| 区分 | 目安 | 必須に近い装備 | 行わないこと |
| --- | ---: | --- | --- |
| A: 本番 | 3〜5アプリ | 外形監視、Sentry、バックアップ復元試験、Security Scan、Oncall、週次レポート | 根拠のない24時間SLAの約束 |
| B: β | 8〜10アプリ | 外形監視、Sentry、Slack通知、Security Scan、週次確認 | Oncall、過剰な冗長化 |
| C: 実験 | 15〜20アプリ | 最小限のログ・エラー監視、手動確認、費用上限 | Oncall、高度な監視、無期限の保持 |

段階は固定しない。利用者、機密性、収益、復旧要件が上がった場合だけ昇格し、利用終了や低リスク化に応じて降格または廃止する。昇格時はA / Bの不足装備をIssueで埋めてから切り替える。

## Devin Security Scan

### 対象と承認

- スキャン対象リポジトリを明示的な許可リストにし、サービス台帳とIssueへ記録する。
- 組織全体を無条件に走査しない。対象ごとに固定した `profile_id` と目的を記録する。
- 初回スキャン、自動スキャン、権限変更は、対象・頻度・プロファイル・通知先を提示して明示承認を得てから作成する。
- Devin MCPの作成系操作は承認カードまたは明示承認を必要とする。作成できたかを成功と決めつけず、設定を読み戻す。

### 初期標準

- 初回は対象リポジトリへ `security/deep` を1回実行する。
- 以降は毎週月曜09:00 JSTに、新規コミットだけを `normal` で確認する案を初期値とする。実行頻度と時刻は費用・ノイズを確認して調整する。
- 自動修正PRは作らない。検出結果をトリアージし、必要性と優先度を人間が決める。
- 修正は別Issue・別セッションで行い、テストと証跡を付けたDraft PRで停止する。

### 結果の扱い

- Critical / Highは `#security-weekly` へ通知し、LINEへはCritical / Highだけを中継する。
- Medium以下も週次でまとめ、誤検知、許容、要修正、監視継続に分類する。
- 修正PRのマージ、本番反映、権限変更は人間の承認後に別工程で行う。

## Devin Oncall

OncallはA段階の本番アプリだけを対象にする。導入前に対象サービス、連絡経路、対応可能時間、エスカレーション、停止条件を決める。

初期構築時点では、Slack連携、通知チャネル、responders、週次レポートが未設定である可能性を前提にする。作成操作を実行しただけでは完了とせず、設定を読み戻し、テスト通知とテストインシデントの結果を確認する。

### 接続と設定

1. Devin側のSlack連携を接続する。接続状態を設定画面と読み取り結果の両方で確認する。
2. `#ops-alerts` と `#security-weekly` を作成または指定する。存在確認とID取得はSlack APIの実レスポンスを使い、チャネル名からIDを推測しない。
3. responders、incident settings、channel prefix、response mode、auto-join、run-as権限を確認する。
4. テスト通知とテストインシデントで、起票、通知、参加、クローズ、レポートを検証する。
5. 週次レポートの送信先と時刻を設定し、最初のレポートを読み戻す。

設定値やネットワーク許可リストは、対象サービスと必要な通信先だけに限定する。資格情報、個人情報、トークン、CookieをIssue、PR、通知本文、証跡へ含めない。

### 通知ルール

- `#ops-alerts`: 稼働監視、例外、インシデント、復旧、定時レポート。
- `#security-weekly`: スキャン結果、脆弱性トリアージ、週次セキュリティ要約。
- LINE: Critical / HighだけをCloudflare Workerなどの中継で送る。Devin Oncallの直接通知先はSlack / Teams / PagerDutyであり、LINEへ直接接続できる前提を置かない。
- LINE Notifyの提供終了を前提とし、新規構成ではLINE Messaging APIを使う。中継では送信元制限、失敗時再送、機密情報のマスキングを実装する。

## 定期運用

### 週次（30〜60分）

- 未対応インシデント、外形監視、Sentryの新規例外を確認する。
- Security Scanの新規findingsをCritical / High / Medium以下に分類し、所有者と期限を決める。
- 自動化が作ったDraft PRを確認し、採用、修正、却下を判断する。
- 再発防止策がIssueとテストへ反映されたか確認する。

### 月次（1〜2時間）

- 1アプリ以上でバックアップからの復元を試験する。
- Secret、権限、不要な連携、費用、監視設定、サービス台帳を見直す。
- β / 実験アプリを昇格、継続、休止、廃止に分類する。
- 廃止対象は告知、データのエクスポート、Secret失効、外部連携解除まで完了させる。

## 導入順序

1. サービス台帳へ全アプリと所有者を登録する。
2. 共通基盤とリリース判定基準を整備する。
3. 各アプリをA / B / Cへ分類する。
4. Slackの運用・セキュリティチャネルを確定し、実チャネルIDを取得する。
5. 対象リポジトリと固定 `profile_id` を承認し、初回Security Scanを実行する。
6. A段階だけでOncallのresponders、通知、レポートを設定し、テストする。
7. テスト済みの中継だけをLINEへ接続する。
8. 週次・月次運用を開始し、件数と作業時間を見て段階数・頻度・費用上限を調整する。

## リリース前チェック

- Issue、受入条件、テスト結果、固定SHAが揃っている。
- Critical / Highの未解決findingがない。例外は理由、期限、承認者がある。
- 監視、通知、ロールバック、バックアップが対象段階の基準を満たす。
- Secretがコミットされておらず、権限が必要最小限である。
- 費用上限と停止条件が設定されている。
- 本番デプロイは人間が承認し、実行後の外形監視とロールバック判断ができる。
