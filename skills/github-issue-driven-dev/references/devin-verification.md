# Devin による独立検証

## 対象の決定

Codex は Issue の受入条件、変更差分、既存テストと `test-board.yaml` の Issue / impact 結果を照合し、E2E とセキュリティの対象を決める。UI やユーザー操作がない文書変更などでは E2E を対象外とし、理由を記録する。セキュリティも対象、検証方法と脅威を具体化する。関係しない全ケースや本番環境を自動で検査しない。`test-board` がない場合は既存のテスト一覧と Issue から計画し、台帳の不足を報告する。

検証は権限のあるリポジトリと指定された隔離環境に限る。認証・実機・データ・環境・予算が不足すれば当該ケースは未検証とし、代替手段と不足を記録する。資格情報、個人情報、トークンや Cookie を Issue、PR、依頼文、ログ、証跡に含めない。必要な秘密情報は既存の安全なシークレット機構で扱う。

## 依頼と追跡

1. 固定した commit SHA を push し、Issue / Draft PR と必要な環境・コマンドを準備する。対象 SHA と PR の head が一致していることを確かめる。
2. 公式 Devin MCP で関連セッションを検索し、同じ対象・目的のものだけ再利用する。なければ検証専用セッションを作る。接続できない場合は未検証と報告し、無断で別サービスに送信しない。
3. 下記を埋めて依頼する。初回は検証のみ。失敗時の修正は Codex が担当範囲を決める。マージ、デプロイ、公開、権限変更、削除、課金追加を依頼しない。
4. 完了を待ち、Issue のコメントと証跡を読み戻す。結果に SHA、コマンド、環境、各ケースの成功・失敗・未実行と理由があることを確認する。未完了、証跡不足、SHA 不一致は成功と扱わない。PR に要約を残し、Issue の記録と一致させる。
5. 修正で SHA が変わったら旧結果を旧 SHA に紐付けたまま残し、影響範囲を再選定し新 SHA で必要な検証をやり直す。台帳の実行履歴は実証済みのケースだけ更新する。最終的なマージとデプロイは人間が判断する。

## 依頼テンプレート

```text
あなたは独立した Checker です。実装を変更せず、以下の固定 commit を検証してください。
Repository: <owner/repo>
Issue: <URL>  PR: <URL または未作成>
Commit SHA: <完全な SHA>  比較対象: <base SHA>
受入条件: <具体的な条件>
対象環境: <OS、実行方法、許可されたテスト環境、テストデータ>
E2E: <ケース ID、操作、期待結果、コマンド。対象外なら理由>
セキュリティ: <変更に関連する脅威、対象、実行する安全な検査。対象外なら理由>
認証状態: <未認証・利用者・権限など該当分。秘密情報は記載しない>
証跡: <ログ、必要な画面・動画と保存先。秘密情報を除去>
制約: 指定環境内のみ。コード変更、PR作成、マージ、デプロイ、公開、権限変更、削除、課金追加は禁止。
結果を Issue コメントに日本語で記録し、コメント URL を返してください。各ケースについて実行環境、SHA、時刻、コマンド、期待と実際、結果、証跡、未実施理由を記載し、全体を「合格」「不合格」「未検証あり」のいずれかで判定してください。権限や環境がなく記録できない場合はその旨と結果を返してください。
```

詳細なテスト設計と台帳形式は、利用可能な `test-case-board` および `loop-engineering-dev` を参照する。GitHub Actions が動かず代替実行した場合は、その事実と差異を明記し、必須チェックの成功と混同しない。
